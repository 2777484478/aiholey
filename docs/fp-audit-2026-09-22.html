一、方法与口径

用当前规则引擎重扫各仓库的工作目录（data/repos/N），与数据库里当时生成的报告逐条对比。这样既能回答「报告里有多少误报」，也能回答「哪些误报已经被治理、哪些还在」。

两点口径说明：① 历史报告是治理之前生成的，DB 中旧数据不会自动刷新，需重新扫描才会用上新规则；② 重扫基于仓库当前工作目录，若中途 pull 过更新，计数与旧报告会有小幅出入，属正常。

三、规则层：当前规则仍会误报的点

以下是「用今天的规则重扫，仍然会报出来、且判定为误报」的清单，按影响面排序。每项都附实际命中行。

1. weak-crypto —— 把「导入包 / 协议名常量」当成「在用弱算法」 误报

35 条命中里约 23 条属于此类。导入一个包、声明一个 SNMP 协议枚举值，都不代表代码真的在用它做加密。

aiopskitcommon/src/github.com/digiwin/utils/crypt/descrypt/descrypt.go:6 "crypto/des"  ← 只是 import
funcresearch/.../reader/config/models.go:384 SnmpReaderAuthProtocolMd5       = "MD5"  ← 协议名常量，不是算法调用
funcresearch/.../reader/config/config.go:1513 ChooseOptions: []interface{}{"", "SHA1", "SSHA1", "SHA256", ...}  ← 下拉选项枚举

同规则里真正的命中是 des.NewCipher(keyBytes)、md5.Sum(data)、new AES(Mode.ECB, ...) —— 这些要保留。

2. path-traversal —— 测试文件未跳过 + Go 类型名误触发 误报

funcresearch/.../windows/perfmon/pdh/pdh_query_windows.go:66 func (q *Query) Open() error {  ← Query 被当成了「外部输入 query」关键字，配合 Open( 命中
aiopskit/src/.../queue/disk_test.go:642 f, _ := os.OpenFile(path.Join(tmpDir, fileName), os.O_RDWR|os.O_CREATE, 0600)  ← 单元测试，该规则未开 skip_tests

另有大量 ioutil.ReadFile(filePath) 类命中：证据仅是「变量名叫 filePath」，这是工具函数而非漏洞。把变量名当作外部输入来源，等于把库函数全报一遍。

3. sql-string-concat —— 测试用例 + WMI 查询串 误报

funcresearch/.../smartinfotest/smartinfotest.go:83 QueryWmiByNamespace("\\root\\wmi", "Select * from MSStorageDriver_FailurePredictThresholds ...")  ← WMI 查询，不是 SQL
aiopskit/src/.../reader/mysqlv2/mysql_test.go:540（同类约 12 条） "mysql_sql": "select * from " + tablename  ← 测试夹具

真正值得看的是 sqls += "Select * From " + tableName + ";" 这类「表名拼接」——表名无法用占位符绑定，是真实的代码味，应保留但降级。

4. file-download-path —— 词边界缺失，fname, 命中 name, 误报

aiopskit/src/.../queue/disk.go:689 log.Errorf("... fail read, set readFileNum with writeFileNum: %d", d.name, d.writeFileNum)

模式里的 (filename|path|file|name) 没有词边界，d.name, 直接命中；readFileNum 也会被算成 readFile。这类命中与「下载路径可控」毫无关系。

5. private-key-block —— 注释里「说明」私钥格式被当成私钥 误报

aiopskitcommon/.../rsacrypt/uiflowdec/ui_flow_dec.go:33 // 嘗試以 PKCS#1 格式解析 (通常以 -----BEGIN RSA PRIVATE KEY----- 開頭)

该规则是刻意扫注释的（注释里残留真实密钥确实是事故），但这里只是文档在描述密钥格式。判据应要求标记之后真有 base64 正文行，或排除「通常以…开头 / 格式为…」这类说明性文字。

6. debug-enabled —— URL 查询串里的 debug=1 误报

aiopskit/src/.../mgr/api_debug.go:138  ·  es_cli/.../pprofhtml/index_html.go:101 link := &url.URL{Path: profile.Href, RawQuery: "debug=1"}

这是 pprof 性能剖析端点的查询参数，与「应用 debug 模式开启」是两回事。

同规则在 repo5 的 6 条命中（new Function(...)、eval(res)）都是真问题。

9. ssrf —— 通用 HTTP 工具类里按变量名刷量 低可信

repo3 的 15 条几乎全部来自 HttpClient.java 这个统一请求封装类，触发条件是参数变量名恰好叫 url：

aioai/src/main/java/com/digiwin/escloud/aioai/common/http/HttpClient.java:68 / 118 / 152 / 198 / 265 / 316 T response = restTemplate.postForObject(url, httpEntity, responseType);
ResponseEntity<T> response = restTemplate.exchange(url, HttpMethod.GET, httpEntity, responseType);

这些是内部服务调用，url 由调用方传入（多为配置拼接），是否可达需看每个调用点。变量名不是污点来源——现有 line_require 里的 \burl\b 太弱，导致「凡是名字叫 url 的请求」都报。建议改成按工具类去重或引入真实来源判据。

注意：这一项是放宽方向的副作用 —— 治理时为覆盖 restTemplate 系 sink 扩大了模式，命中数从 5 涨到 15。收紧与放宽都要双向验证，这里正是一个例子。

四、AI 层误报：主要形态是「假设式结论」

AI 层的问题与规则层不同 —— 不是「匹配了错误字符串」，而是基于看不到的代码推测出漏洞，并给出 critical/high。run2 的 27 条里 23 条、run3 的 28 条里 22 条含「可能 / 若…则 / 未给出实现 / 未在代码中显式出现」这类措辞。

典型实例

run9  src/app/utils/index.ts:13  误报 · critical 标题「硬编码 RSA 公钥泄露（含密钥材料）」。实际该行是 const PUBLIC_KEY = 'MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A...' —— 是公钥。公钥本就要下发到前端用于加密，报成 critical 是典型的严重度失真。
run9  src/app/services/myDevice.service.ts:5  误报 · critical 「encrypt/decrypt 工具函数可能隐含硬编码密钥……若 utils.ts 中 encrypt 函数使用固定密钥」—— 全篇建立在「看不到实现」的假设上。
run2  aiogateway/.../mapper/SupplierMapper.java:12  自我否定却给 critical 「MyBatis @Select 注解中硬编码 SQL 且无参数化，存在注入风险」，正文却写「虽然当前 SQL 为静态无参查询……属于高危代码模式」。当前无注入点，却是 critical。
run2  RequestParamFilter.java:186  误报 · high 「虽然当前代码未直接使用 SpEL，但 getHeaderValueIgnoreCase 若内部调用 …可能触发 SpEL 表达式求值」
run9  apiRequest.ts:32 / :149、token-renewal.service.ts:18  不是漏洞 「默认 content-type 固定为 form-urlencoded」标成不安全配置；「clearAllCookie 清除全部 Cookie」标成敏感数据暴露；「tokenAcquiredAt 时间戳暴露用户活跃模式」—— 这三条属于设计取舍，不是漏洞。

机制层面的一个缺陷

findings.confidence 字段目前没有区分度：规则层全部是 medium；AI 层 90 条标 high、14 条 medium —— 即投机结论也拿 high。这个字段本可用来提示可信度，现在起不到作用，反而制造了「高置信」的错觉。

新增的四种约束能力

能力解决什么
context_require「本行 + 下一行」拼窗口匹配 —— 行级正则表达不了 PEM 这种「标记在上、正文在下」的结构
file_contains + EXTERNAL_INPUT_HINTS文件级判据：正则是逐行的，看不到跨行数据流；「这个文件接不接外部输入」由整个文件回答
severity_downgrade形态成立但危险性明显更低的子类降一级、置信度同时压低，而不是整条丢掉（表名拼接：critical→high 且置信度→low）
规则自带 confidence结构性证据（私钥块 / AKIA 密钥）标 high，只凭 sink 形态的（ssrf / 路径穿越）标 low，界面与报告都会显示

AI 层：从「提示词请求」变成「代码兜底」

提示词里加了证据门槛（结论必须由可见代码支撑、critical 不得出现在假设句、 公钥与静态 SQL 不是漏洞）；同时加了一层确定性兜底：命中假设式措辞 （可能 / 若 / 未展示 / 未在代码中 / 无法确认）就降一级（critical→high、high→medium） 并把 confidence 压到 low —— 不丢结论，但明确标成「需人工确认」。 这一层单独立了测试（backend/tests/test_ai_calibration.py）。

刻意没改的（诚实记账）

  • 日志拼接 3 条（log.error("..." + requestId)）：形态确实是字符串拼接进日志， 属于低价值线索，保留下来由人扫一眼，没为它加特例。
  • 打包脚本的 1 条命令执行：os.popen('GOARCH=%s go build …' % (arch,)) 的 %s 填的是本地常量。行级判据分不清「% 后面是常量还是外部输入」，保留待人工确认。
  • 表名拼接 9 条：保留了（表名无法用占位符绑定，是真实代码味），只是不再算 critical。
  • 历史报告不会自动变：数据库里已入库的旧结论仍是旧数据，需要重新扫描才会用上新规则。
